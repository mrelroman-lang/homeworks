# Предложение по организации инфраструктуры для микросервисной архитектуры

## Задача 1. Разработка: Git + CI/CD в облаке

### Предлагаемое решение
**GitLab (SaaS или Self‑managed в облаке) + GitLab CI/CD + GitLab Container Registry + GitLab Runners (в т.ч. self-hosted).**

### Архитектура и принципы взаимодействия
- **Система контроля версий:** GitLab Git (один репозиторий на микросервис).
- **CI/CD:** GitLab CI/CD, пайплайны описываются в `.gitlab-ci.yml` в каждом репозитории; сборка запускается по событиям (push, merge request, теги) и вручную с параметрами.
- **Агенты сборки:** GitLab Runners (Kubernetes/docker/exec), в т.ч. собственные сервера (self-hosted), с поддержкой параллельных джоб.
- **Артефакты и образы:** GitLab Container Registry для Docker-образов; кэширование зависимостей и артефактов сборки.
- **Секреты:** GitLab CI/CD Variables (masked/protected), интеграция с HashiCorp Vault.

### Соответствие требованиям

| Требование | Как реализуется в GitLab |
|---|---|
| Облачная система | GitLab.com (SaaS) или GitLab Self-managed в вашем облаке (Yandex Cloud / др.) |
| Git, репозиторий на сервис | Native Git, один проект/репозиторий на микросервис |
| Сборка по событию из VCS | Triggers: push, MR, tag, schedule; webhooks |
| Сборка по кнопке с параметрами | Manual jobs + `variables` в UI; `trigger` API с переменными |
| Настройки к каждой сборке | `.gitlab-ci.yml` + CI/CD Variables (project/group/env) |
| Шаблоны конфигураций сборок | `include` + template repositories; group-level CI templates |
| Безопасное хранение секретов | Masked/protected variables; интеграция с Vault |
| Несколько конфигураций из одного репо | Multiple pipelines/jobs, rules, matrix builds, environments |
| Кастомные шаги при сборке | Любые `script` шаги в джобах; динамические пайплайны |
| Собственные Docker-образы для сборки | `image:` в job; build & push в Container Registry |
| Агенты на собственных серверах | Self-hosted GitLab Runners (docker/kubernetes/shell) |
| Параллельный запуск сборок | Конкурентные пайплайны, `parallel` в job, autoscaling runners |
| Параллельный запуск тестов | `parallel` + разделение тестов по джобам; кэш зависимостей |

### Почему GitLab
- **Единая платформа:** VCS + CI/CD + Registry + Security + Packages в одном продукте, что снижает операционные издержки и упрощает управление доступом.
- **Гибкость пайплайнов:** Декларативные YAML-пайплайны, шаблоны, матричные сборки, ручные шаги, environments и promotion gates.
- **Масштабируемость:** Поддержка тысяч параллельных джоб через автоскейлинг runners (Kubernetes), кэширование и артефакты.
- **Безопасность:** Protected variables, OIDC для облачных провайдеров, интеграция с Vault, audit logs.
- **Экосистема:** Интеграции с Kubernetes, облачными registry, сканерами уязвимостей, SAST/DAST.

## Задача 2. Логи: централизованный сбор, поиск, UI

### Предлагаемое решение
**Grafana Loki + Promtail/Fluent Bit + Grafana (Loki datasource).**

### Архитектура и принципы взаимодействия
- **Агенты сбора:** Promtail (нативный для Loki) или Fluent Bit на каждом хосте/ноде Kubernetes; читают stdout/stderr контейнеров и файлов.
- **Транспорт и буферизация:** При высоких нагрузках — Kafka/Redpanda между агентами и Loki для гарантированной доставки и replay.
- **Хранилище:** Loki хранит логи с метками (label-based), данные в объектном хранилище (S3-совместимое) — дёшево и масштабируемо.
- **Поиск и UI:** Grafana предоставляет Loki Explore, сохранённые запросы, дашборды; доступ разработчиков через RBAC Grafana/OAuth.
- **Ссылки на сохранённый поиск:** В Grafana можно сохранить запрос и поделиться ссылкой (deep link) с параметрами времени и фильтрами.

### Соответствие требованиям

| Требование | Как реализуется |
|---|---|
| Сбор логов в центральное хранилище со всех хостов | Promtail/Fluent Bit на каждом хосте → Loki (central) |
| Минимальные требования к приложениям, stdout | Сбор stdout/stderr контейнеров; без изменений в коде |
| Гарантированная доставка | Буферизация на агенте + опционально Kafka между агентом и Loki |
| Поиск и фильтрация по записям | LogQL в Loki: фильтрация по меткам и содержимому |
| UI для разработчиков | Grafana Explore + дашборды; RBAC для команд |
| Ссылка на сохранённый поиск | Сохранённые запросы в Grafana + shareable URL |

### Почему Loki + Grafana
- **Экономичность:** Loki не индексирует полный текст, а использует метки — в 5–10 раз дешевле Elasticsearch при больших объёмах.
- **Kubernetes-нативность:** Promtail автоматически обнаруживает поды, использует те же метки, что и Prometheus (namespace, pod, app).
- **Единый UI с мониторингом:** Grafana объединяет метрики (Prometheus) и логи (Loki) в одних дашбордах, упрощая расследование инцидентов.
- **Гибкость:** Поддержка полнотекстового поиска через доп. стек (OpenObserve/Elasticsearch) при необходимости, но для большинства команд Loki достаточен.

## Задача 3. Мониторинг: метрики хостов и сервисов

### Предлагаемое решение
**Prometheus + Grafana + Node Exporter + сервисные экспортеры (или встроенные `/metrics`).**

### Архитектура и принципы взаимодействия
- **Сбор метрик хостов:** Node Exporter на каждом сервере → CPU, RAM, disk, network.
- **Сбор метрик сервисов:** Каждый микросервис экспонирует `/metrics` (Prometheus-format); Prometheus автоматически обнаруживает цели через Kubernetes SD или статические конфиги.
- **Специфичные метрики сервисов:** Инструментирование через клиентские библиотеки (Prometheus client) — бизнес-метрики, latency, error rate.
- **Хранение и запросы:** Prometheus (TSDB) хранит метрики; PromQL для запросов и агрегаций.
- **UI и дашборды:** Grafana подключается к Prometheus как datasource; команды создают панели, алерты, переменные для фильтрации по сервисам/неймспейсам.

### Соответствие требованиям

| Требование | Как реализуется |
|---|---|
| Сбор метрик со всех хостов | Node Exporter на каждом хосте → Prometheus |
| Метрики ресурсов хостов (CPU/RAM/HDD/Network) | Node Exporter стандартные метрики |
| Метрики ресурсов на сервис | cAdvisor (в K8s) или Prometheus-совместимые экспортеры |
| Специфичные метрики сервиса | Инструментирование `/metrics` в коде сервиса |
| UI с запросами и агрегацией | Grafana + PromQL (query builder, переменные) |
| Настраиваемые панели | Grafana dashboards, библиотеки панелей, templating |

### Почему Prometheus + Grafana
- **Стандарт де-факто для микросервисов:** Широкая поддержка в экосистеме, множество готовых дашбордов и алертов.
- **Гибкая модель сбора:** Pull-модель с service discovery, возможность федерации и многоуровневой архитектуры (global/cluster/app Prometheus).
- **Мощный язык запросов:** PromQL позволяет строить сложные агрегации, SLO/SLI, record rules.
- **Интеграция с логами и трассировками:** Grafana объединяет Prometheus, Loki и Tempo в единый observability UI.
