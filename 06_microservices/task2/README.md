# Предложение по организации инфраструктуры для микросервисной архитектуры

## Задача 1: API Gateway

### Сравнительная таблица решений

| Критерий | NGINX Plus | Kong | Traefik |
| :--- | :--- | :--- | :--- | 
| **Маршрутизация на основе конфигурации** | Да (Path, Regex, Rewrite) | Да (Routes, Services) | Да (Rules, Middlewares) |
| **Аутентификация** | JWT, OIDC, SAML, OAuth 2.0 | Key, Basic, OAuth 2.0, JWT, HMAC | ForwardAuth, JWT (через middleware) |
| **Терминация HTTPS** | Да | Да | Да (автоматический Let's Encrypt) |
| **Cloud-Native / K8s** | Средняя | Средняя | Высокая (нативная) |
| **GitOps** | Низкая | Средняя | Высокая |
| **Стоимость** | Open Source + Commercial | Open Source + Commercial | Open Source + Enterprise |

### Выбор решения

Для крупной компании с микросервисной архитектурой рекомендую **Kong**.

**Обоснование:**

1. **Функциональная полнота:** Kong из коробки закрывает все три требования. Он имеет богатый набор плагинов для аутентификации (JWT, OAuth2, Key Auth), умеет маршрутизировать запросы и легко справляется с терминацией SSL.
2. **Экосистема:** Наличие открытого ядра (Open Source) и коммерческой поддержки позволяет начать с малого и масштабироваться без смены технологии.
3. **Управление конфигурацией:** Поддерживает декларативный подход (decK), что критично для DevOps-практик и GitOps, позволяя хранить конфигурацию шлюза в репозитории и версионировать её.
4. **Гибкость:** Kong хорошо интегрируется с современными стеками (Kubernetes, Docker), хотя и требует чуть больше настройки, чем Traefik, он дает больше контроля для сложных корпоративных сценариев.

## Задача 2: Брокер сообщений

### Сравнительная таблица решений

| Критерий | Apache Kafka | RabbitMQ | NATS JetStream | ActiveMQ Artemis |
| :--- | :--- | :--- | :--- | :--- |
| **Кластеризация** | Да (KRaft, MirrorMaker) | Да (Quorum Queues) | Да (Raft) | Да |
| **Хранение на диске** | Да (Log segments) | Да (Quorum Queues) | Да | Да (Journal) |
| **Высокая скорость** | Очень высокая (потоки) | Высокая (очереди) | Очень высокая | Средняя |
| **Форматы сообщений** | Opaque, Key-Value | Opaque, MIME, Priority | Opaque | Opaque, Object (JMS) |
| **Права доступа (ACL)** | Да (Topic-level) | Да (Vhost/Queue) | Да (Account/Subject) | Да |
| **Простота эксплуатации** | Сложная | Средняя | Низкая | Высокая |

### Выбор решения

Для данной задачи рекомендую **RabbitMQ** с использованием **Quorum Queues**.

**Обоснование:**

1. **Баланс требований:** RabbitMQ подходит под требование "простота эксплуатации" в сочетании с надежностью. Он проще в настройке и мониторинге, чем Kafka, и имеет огромное количество готовых интеграций.
2. **Надежность и хранение:** Переход на **Quorum Queues** (на основе алгоритма Raft) обеспечивает надежное хранение сообщений на диске и отказоустойчивость кластера, что полностью закрывает требование о кластеризации и персистентности. Это современная замена устаревшим зеркальным очередям.
3. **Управление доступом:** RabbitMQ имеет гибкую систему прав доступа на уровне виртуальных хостов (vhost) и очередей, что позволяет легко разделять права между командами.
4. **Производительность:** Хотя Kafka быстрее на огромных потоках данных, RabbitMQ показывает отличную скорость для стандартных бизнес-задач, особенно в JVM-среде (Spring Boot). Для большинства микросервисных сценариев скорости RabbitMQ более чем достаточно.

**Почему не другое:** Kafka — это промышленный стандарт, но сложна в эксплуатации и требует больше ресурсов для поддержки.
ActiveMQ Artemis проще чем Kafka, но уступает RabbitMQ по размеру сообщества, количеству готовых плагинов и популярности в современных cloud-native микросервисах.
